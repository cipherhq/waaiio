## 2026-11-17 — Failure tracking: reportFailure() with strict scrubbing (Issue #1092)

- **Why:**
  - Owner decision 2026-11-16 (#1079): track as many failures as we can so future bugs are easy to find. Many failures were only console-logged (payment webhooks, saved-card charges, follow-ups, cron jobs, Custom Flow, WhatsApp sends) or reached Sentry without any business/area context.
- **What changed:**
  - `lib/observability/report-failure.ts` (new): `reportFailure(error, ctx)` sends one Sentry event and one `failure.reported` log line. Only allowlisted fields leave it (area, op, business/payment/session/flow UUIDs, flow type, step, capability, gateway, cron job, error class, error code, HTTP status, request/run id, short commit SHA); every string must be a UUID or pass `isSafeIdentifier()`. The error's free-form message is never sent (only its class name and stack frames). Never throws, never awaits, throttled to 20 Sentry events per fingerprint per minute per instance.
  - `lib/sentry-redact.ts`: the shared `beforeSend` also strips breadcrumbs, request body/query/cookies, user and extra from events built by `reportFailure` (tag `failure_report`). Other events are unchanged.
  - Wired beside existing logs (no return/throw/send changed): `lib/bot/bot.service.ts` (handleMessage crash — replaces the untagged raw `Sentry.captureException`), `lib/bot/flows/executor.ts` (batch send failure), `lib/channels/message-sender.ts` (provider send failure, still rethrown), `app/api/webhook/meta-cloud/route.ts` (processing, fallback reply, outer catch), `app/api/payments/webhook/route.ts` (12 Paystack failure points), `app/api/payments/stripe-webhook/route.ts` (10 Stripe failure points), `lib/payments/charge-saved.ts` (4 saved-card failure points), `lib/payments/authority.ts` (critical effects failed, completion RPC error), `lib/payments/send-confirmation.ts` (`logSafeError`, 36 post-payment points), `lib/payments/transaction-followup.ts` (5 silent DB-read failures), `lib/bot/custom-flow/engine.ts` (entitlement, handoff check, unchecked `custom_flow_logs` insert error), `lib/observability/cron.ts` (`failed`/`itemFailed`), and the 500 exits of 22 cron routes.
  - Tests: `lib/__tests__/report-failure.test.ts` (privacy: secrets, card numbers, CVV/PIN, phones, emails, message bodies and provider text never reach Sentry or the log; never-throws; throttle; beforeSend scrub), `lib/__tests__/report-failure-wiring.test.ts` (behaviour preserved at cron logger, follow-up resume, sender rethrow, Custom Flow log insert).
- **Affects:** Sentry gets more, better-grouped events (area/op tags, business id). Logs get one extra `failure.reported` line per failure.
- **Unchanged:** every customer message, payment, retry, webhook response code and return value. No migration, no new tooling, no Sentry/PostHog production setting.
- **What could break:** Sentry quota use rises during an outage (throttle limits it per instance). Existing raw `Sentry.capture*` calls elsewhere are left as they were.
