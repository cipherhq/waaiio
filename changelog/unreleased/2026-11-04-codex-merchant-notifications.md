## 2026-11-04 — Merchant notifications (#811 / #813): renumbered migrations, longer invitations, protected-staging confirmation

- **Renumbering (Owner decisions 2026-11-04: option A, staging plan S1).** Migrations `499_merchant_notifications`, `502_merchant_notification_invitation_lifetime` and `510_merchant_notification_pre_emission_recovery` are now `511`, `512` and `513`, above the Release V3 lock. Their verifier labels read M511, M512 and M513. The SQL logic is unchanged. Catalog deltas for 511 to 513 come from the PG17 oracle. Staging's earlier 499 and 502 are removed by `scripts/release-v3/staging-813-teardown.sql` (#872, separate Owner approval) and then re-applied as 511 and 512 by the release.
- **M511 capture function permissions (Owner decision 2026-11-04, option A).** `capture_merchant_notification()` is a trigger function and not an API. 511 now also revokes EXECUTE from `service_role`, so only `postgres` can call it directly in every environment. Before this, staging (no default privileges in `public`) and production (default EXECUTE for `service_role`) ended with different permissions, and the Release V3 gate would refuse staging after 511 was applied. The trigger still fires for every writer, because EXECUTE is checked when a trigger is created, not when it fires. The 511 verifier now fails if `service_role` can execute the function. The 511 catalog delta was regenerated by the CI oracle. Tests: `merchant-notifications-811.pg.test.ts` applies 511–513 under production's default privileges and checks that the trigger fires for a `service_role` insert. It also has a verifier tamper case.
- **M512** extends newly issued email and WhatsApp notification invitations to 48 hours. Existing invitation expiry is unchanged. The email invitation copy reflects the new lifetime. Replacement, rate limits, token binding, revocation and idempotent consent replay are unchanged.
- **`app/notifications/confirm/page.tsx`** sends same-origin credentials, so deployment access cookies accompany explicit invitation confirmation. Token verification and consent are still required. Regression test: `components/dashboard/__tests__/merchant-notifications-811.test.tsx`.
- **Lock order fix (review r2-813-sync).** The WhatsApp fence (M513) now locks the business row before the recipient, and allowance reservation (M511) uses `FOR NO KEY UPDATE`, so a fence can no longer deadlock a merchant order, booking or payment write. Test: `merchant-notifications-811.pg.test.ts`.
- **Hardening (Owner decision 2026-11-05).** A merchant's order, booking, reservation or payment write always succeeds: if its alert cannot be captured, the alert is skipped with a database warning (M511 capture). The fence reads the recipient `FOR SHARE` (M513), and recovery uses `FOR NO KEY UPDATE` on the business (M513), so neither can deadlock or block merchant foreign-key checks. Tests: `merchant-notifications-811.pg.test.ts`.
- **Could break:** M512 must be applied before the updated email copy is deployed. Cookie transport to the same-origin confirmation endpoint. No payment behaviour changes. Nothing is applied to a hosted environment by this PR.
