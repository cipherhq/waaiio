## 2026-11-05 — Weekly payouts use the merchant's own completed week (#796)

- **What changed:** New `lib/payouts/period.ts` (`getPrecedingCompletedWeek(now, timezone)`) picks the last fully finished Monday–Sunday week in the merchant's stored IANA timezone (`businesses.timezone`). It returns local date labels for `period_start`/`period_end` and half-open UTC query bounds `[local Monday 00:00, next local Monday 00:00)`. A Sunday run picks the week before, never the unfinished current week. An invalid or missing timezone fails closed: that business is skipped and counted as failed.
- `app/api/admin/payouts/generate/route.ts`: the period is worked out per business, after the accounting-hold skip. Fee and velocity reads use `.gte(queryStart).lt(queryEnd)` instead of the old server-time bounds, which kept the time of day of the run and could leave part of the week out. Responses and the admin audit entry carry `period` when every processed business shares one week, and `periods` otherwise.
- `app/api/cron/auto-payout/route.ts`: businesses are grouped by period. Duplicate checks and fee reads run once per group, and the other batch reads run once. Businesses with an invalid timezone are left out of both generation and held-payout release. The kill switch (`ENABLE_PAYOUTS`) and cron auth are unchanged.
- `vercel.json`: the auto-payout cron moves from Monday 06:00 UTC to **Monday 12:00 UTC** (Owner decision 2026-11-05). At 06:00 UTC it is still Sunday in US/Canada Mountain time, so with merchant-local weeks one week was skipped every spring and one repeated every autumn (simulated: 1–7 March 2027). Pacific, Alaska and Hawaii merchants were also always a week behind. At 12:00 UTC it is Monday in every zone of the five countries. Nigeria, Ghana and UK runs now start six hours later on Monday.
- `createPrecedingWeekResolver(now)` in `lib/payouts/period.ts` works out each timezone's week once per run. Both routes use it. One calculation takes about 0.1–0.2 s (DST probing in `naiveToUtc`), and the cron has a 60 s limit, so calculating it per merchant could run out of time with a few hundred merchants.
- **Each payout starts where the last recorded payout ended (Owner decisions 2026-11-05: Option A, and "fix it in #796 now"; needs M521, PR #918).**
  - **The read:** both routes read the business's own payout history for the last 53 weeks, one read per business. A full 1000-row page counts as unreadable, because the API caps responses at 1000 rows: the manual route counts that business as failed, and the cron skips it.
  - **The range:** `anchorCoveredRange` (`lib/payouts/period.ts`) picks it:
    - a week that already has a payout in another currency reuses that range;
    - otherwise it starts at the latest recorded `covered_to` of any earlier week, or at local Monday 00:00 if there is none;
    - it always ends at the next local Monday 00:00.
  - **Fails closed:** a range that would be empty or overlap another recorded payout. The manual route counts it as failed; the cron leaves it out of generation and held-payout release. New payouts write `covered_from`/`covered_to`.
  - **Effect:** a timezone change can no longer make two payouts count the same sales, or leave sales between payouts uncounted. Fees from weeks that made no payout (no sales, below the minimum, accounting hold) now roll into the next payout, as the cron's "will accumulate" comment always said. Found by four independent reviews of #796.
  - **Limits:**
    - rows written before M521 (all 11 production rows, July 2026) have no recorded range, so a merchant's first new payout starts at local Monday 00:00. The weeks since July need a separate catch-up decision;
    - a quiet stretch of more than 53 weeks also restarts at local Monday 00:00;
    - a longer range counts more payments in the velocity check, so a roll-forward payout is more likely to be held for review.
- `admin/src/pages/Payouts.tsx`: the generation message also lists `periods` when businesses fall in different local weeks. The manual route returns no period field when nothing was processed (same as the cron). The cron's doc comment now says Monday 12:00 UTC.
- **Unchanged:** admin authorization and step-up, custody classification (connected-provider payments vs Waaiio-held funds), fee formulas, transfer writers, enablement switches and existing payout rows. Connected-provider payments and Waaiio-held manual settlement stay separate.
- **Tests:** `lib/__tests__/payout-period.test.ts` (Sunday, year boundary, DST, dateline, invalid zone; reads the cron schedule from `vercel.json` and checks every supported-country zone gets each week exactly once across the 2027 clock changes, with a control showing the old 06:00 time fails; resolver caching and fail-closed) and `lib/__tests__/payout-period-routes.test.ts` (route handlers with mocked database: anchoring after a timezone change, overlap fails closed in both routes, paired cron release control). `anchorCoveredRange` unit tests include a merchant alternating between `Etc/GMT+12` and `Pacific/Kiritimati` every week: every range starts exactly where the previous ended. Existing payout test fixtures gained a `timezone` field, `.lt`/`.limit` mocks for the new reads, and a `created_at` on cron fee rows; no assertion was weakened (the mixed-timezone cron test checks the per-group read's lower bound instead of two label filters, and adds range and exclusive-end checks).
- **Could break:** response consumers that always expect `period` get `periods` when businesses fall in different local weeks. New `business_payouts` period labels are merchant-local dates. A zone whose clocks jump over Monday 00:00 fails closed for the weeks that start or end on that jump (up to two; none of Waaiio's five countries does this). **Deploy order:** M521 must be applied to staging and production before this code deploys; without the columns the payout reads fail and generation stops safely. Payouts stay switched off (`ENABLE_PAYOUTS` absent).
