## 2026-11-05 — M521: payouts record the exact time range they covered (#796)

- **What changed:** new migration `supabase/migrations/521_payout_covered_range.sql` adds `business_payouts.covered_from` and `covered_to` (nullable `timestamptz`, no default). They record the half-open range of `platform_fees.created_at` a payout counted. A named CHECK (`business_payouts_covered_range_check`) allows both NULL (existing rows) or both set with `covered_from < covered_to`. No grants change: anon and authenticated still cannot insert or update payouts (M439), service_role writes them, and reads stay under the existing RLS (admins, owning business). A self-check fails the migration on drift.
- **Owner decision 2026-11-05 (#796, Option A):** the next week's payout starts where the previous payout ended, so a timezone change can no longer make two payouts count the same sales, or leave sales uncounted. The app change that uses these columns is #796; it ships only after this migration is applied to staging and then production, each with its own Owner approval.
- **Tests:** `lib/__tests__/payout-covered-range-521.pg.test.ts` (real PostgreSQL, live production fixture read 2026-11-05): columns and NULLs on existing rows, idempotent re-run, valid range accepted and empty/reversed/half-set ranges rejected, anon/authenticated cannot write, RLS reads unchanged, self-check fails on ACL drift. Wired into CI's PostgreSQL job. Catalog delta: `supabase/catalog-deltas/521_payout_covered_range.json`. Registry: 521 reserved.
- **Could break:** nothing reads or writes the columns until #796 deploys. Code that inserts payouts with only one of the two columns set would be rejected by the CHECK.
